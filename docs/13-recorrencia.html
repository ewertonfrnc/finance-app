Identidade da ocorrência
⚠️ GET /transactions/:id retorna o template (a date de início da série), não a ocorrência tocada. Para deletar/editar "apenas este", a date da ocorrência precisa viajar pela rota (/transaction/[id]?date=YYYY-MM-DD) e ser usada nos escopos — nunca transaction.date da tela de edição.
🔁
Como o backend entrega recorrência

É importante entender o modelo antes de codar: o banco guarda uma linha por série recorrente (o template). Ao listar transações de um mês, o PostgreSQL usa generate_series para expandir esse template em ocorrências virtuais. O app recebe o resultado como se fossem transações normais.

Consequência direta no app
Todas as ocorrências de uma série compartilham o mesmo id (o id do template). Para identificar uma ocorrência específica, o par (series_id, date) é necessário. Duas implicações que não eram óbvias: (1) listas que renderizam um mês inteiro recebem várias ocorrências diárias/semanais com o mesmo id — o keyExtractor precisa de uma chave própria (occurrenceKey); (2) a date da ocorrência só existe na listagem expandida — o detalhe (GetByID) devolve a data do template. Logo a data tocada deve ser propagada pela navegação.
Contrato assimétrico — atenção ao implementar
O backend lê o escopo em lugares diferentes para cada verbo: DELETE /transactions/:id?scope=…&date=… usa query params (chave date); já o PATCH /transactions/:id lê scope e instance_date do corpo JSON. Não dá para reutilizar a mesma forma de envio nos dois.

Contrato real do backend — já implementado 4 lacunas resolvidas

As 4 lacunas que o plano apontava no guia da API (UpdateRecurring, Scans, SQL de totais/saldo, campo Tags) já foram fechadas no código (internal/store/transactions.go + cmd/api/transactions.go). Use a tabela abaixo como contrato de verdade — confira sempre contra o handler, não contra o guia.

CREATE · POST /v1/transactions
Aceita recurrence e recurrence_end_date
Body: { type, amount, description, date, tags?, recurrence?, recurrence_end_date? }. recurrence é omitempty (default none no Go). Se recurrence != none, o backend gera o series_id sozinho. Resposta inclui recurrence, series_id e recurrence_end_date.
LIST · GET /v1/transactions
Ocorrências já vêm expandidas via generate_series
Cada ocorrência traz a date daquela instância, mas o mesmo id/series_id do template. Exceções (deletes "single") são filtradas por transaction_exceptions. O app não calcula nada de calendário.
DELETE · DELETE /v1/transactions/:id
Escopo em query params: ?scope=&date=
Se a transação tem series_id, o handler exige scope (default single) e, para single/following, a date da ocorrência (query key literal date). Avulsa: DELETE direto, sem params. 204 No Content.
UPDATE · PATCH /v1/transactions/:id
Escopo no corpo JSON: scope + instance_date
UpdateRecurring implementa os 3 escopos. single = exceção + nova avulsa; following = trunca série + novo template; all = UPDATE no template (só type/amount/description propagam — date não). ⚠️ diferente do delete, o escopo vai no body, não na query.
O que isso destrava no plano
Slice 5 não tem mais bloqueio de backend. O foco do app passa a ser puramente client-side: tipos, identidade de ocorrência (occurrenceKey + date na rota) e os dois sheets de escopo.

Slice 1 types/api.ts — novos tipos e campos

RecurrenceType e RecurrenceScope (usado por delete e update). Atualizar ApiTransaction, ApiCreateTransactionPayload e ApiUpdateTransactionPayload. O delete leva o escopo na query (ApiDeleteScopeParams); o update leva no corpo (scope + instance_date).

src/features/transactions/types/api.ts
// Tipos compartilhados (escopo serve para delete E update)
export type RecurrenceType  = "none" | "daily" | "weekly" | "monthly" | "yearly";
export type RecurrenceScope = "single" | "following" | "all";

export interface ApiTransaction {
  id:          string;
  type:        TransactionType;
  amount:      number;
  description: string;
  date:        string;
  created_at:  string;
  updated_at:  string;
  user_id:     string;
  tags?:       ApiTagRef[];
  recurrence:           RecurrenceType;    // novo — sempre presente
  series_id?:           string;            // novo — presente se recorrente
  recurrence_end_date?: string;            // novo — "YYYY-MM-DD" ou undefined
}

export interface ApiCreateTransactionPayload {
  type:        TransactionType;
  amount:      number;
  description: string;
  date:        string;
  recurrence?:           RecurrenceType;   // novo — omitido = "none" no backend
  recurrence_end_date?:  string;           // novo — backend já aceita "YYYY-MM-DD"
}

// UPDATE: escopo vai no CORPO do PATCH
export interface ApiUpdateTransactionPayload {
  type?:        TransactionType;
  amount?:      number;
  description?: string;
  date?:        string;
  scope?:         RecurrenceScope;        // novo — só recorrentes
  instance_date?: string;                 // novo — data da ocorrência (single/following)
}

// DELETE: escopo vai na QUERY STRING (chave literal "date")
export interface ApiDeleteScopeParams {
  scope: RecurrenceScope;
  date?: string;  // "YYYY-MM-DD" — obrigatório para "single" e "following"
}

O mapper é o único ponto de conversão API → domínio. Ao adicionar campos aqui, eles aparecem em todo lugar que usa Transaction. O recurrence ?? "none" garante compatibilidade caso o backend omita o campo (transações antigas antes da migration).

src/lib/mappers.ts
export function mapApiTransaction(raw: ApiTransaction): Transaction {
  const date = raw.date.split("T")[0];
  return {
    id:          raw.id,
    type:        raw.type,
    amount:      raw.amount,
    description: raw.description,
    date,
    createdAt:   raw.created_at,
    updatedAt:   raw.updated_at,
    userId:      raw.user_id,
    tags: (raw.tags ?? []).map((t) => ({ id: t.id, name: t.name, color: t.color })),
    recurrence:         raw.recurrence ?? "none",  // novo
    seriesId:           raw.series_id,             // novo
    recurrenceEndDate:  raw.recurrence_end_date,   // novo
    occurrenceKey:      raw.series_id ? `${raw.series_id}:${date}` : raw.id,  // novo
  };
}
Por que ?? "none" no recurrence?
A migration 000008 tem DEFAULT 'none' e o backend já inclui recurrence no RETURNING e nos Scans, então toda resposta traz o campo. O fallback ?? "none" é cinto-e-suspensório barato: protege contra respostas antigas em cache ou variações de contrato sem custo.
Slice 1 + 4 transactions.service.ts — delete e update com escopo
Correção em relação à 1ª versão do plano
O delete e o update não usam o mesmo mecanismo. deleteTransaction manda o escopo na query ({ params } do Axios → ?scope=…&date=…). Já updateTransaction manda scope e instance_date dentro do corpo do PATCH — é assim que o handler Go lê (UpdateTransactionPayload.Scope / .InstanceDate).
src/features/transactions/services/transactions.service.ts
// DELETE → escopo na QUERY STRING
export async function deleteTransaction(
  id: string,
  params?: ApiDeleteScopeParams,
): Promise<void> {
  await apiClient.delete(`/v1/transactions/${id}`, { params });
}

// UPDATE → scope e instance_date fazem parte do PAYLOAD (corpo)
export async function updateTransaction(
  id: string,
  payload: ApiUpdateTransactionPayload,  // já inclui scope?/instance_date?
): Promise<Transaction> {
  const response = await apiClient.patch<ApiResponse<ApiTransaction>>(
    `/v1/transactions/${id}`,
    payload,  // ← sem { params }; o escopo viaja no corpo
  );
  return mapApiTransaction(response.data.data);
}
Slice 4 app/transaction/[id].tsx — handleDelete com escopo

O handleDelete atual chama remove(id) diretamente. A nova lógica bifurca: se seriesId existe, abre o sheet; caso contrário mantém o comportamento atual (zero regressão para avulsas). ⚠️ A data enviada é a date da rota (a ocorrência que o usuário tocou), porque transaction.date aqui é a data do template, não da ocorrência.

app/transaction/[id].tsx — handleDelete atualizado
const { id, date: occurrenceDate } = useLocalSearchParams<{
  id: string; date?: string;
}>();
const [showDeleteSheet, setShowDeleteSheet] = useState(false);

function handleDelete() {
  if (transaction.seriesId) {
    setShowDeleteSheet(true);  // abre sheet de escopo
    return;
  }
  // avulsa — comportamento original mantido
  remove({ id }, { onSuccess: handleDeleteSuccess });
}

function handleDeleteWithScope(scope: RecurrenceScope) {
  remove(
    { id, scope, date: occurrenceDate },  // ← data da OCORRÊNCIA (rota)
    {
      onSuccess: () => {
        setShowDeleteSheet(false);
        handleDeleteSuccess();
      },
    },
  );
}

function handleDeleteSuccess() {
  router.back();
  invalidate();
  queryClient.removeQueries({ queryKey: queryKeys.transaction(userId, id) });
}

export function useDeleteTransaction() {
  return useMutation({
    mutationFn: ({
      id,
      scope,
      date,

      id: string;

Qual padrão de bottom sheet usar?

O RecurrenceSelector deve aparecer no modo edit?
Para transações avulsas em edit, faz sentido permitir torná-las recorrentes? Isso muda o comportamento do backend — seria um update que adiciona recurrence e series_id. Complexidade adicional vs. UX conveniente.

O backend já aceita recurrence_end_date no create — é só decisão de UI. Permitir definir quando a série termina (ex: "assinar por 12 meses") aumenta a qualidade, mas adiciona um campo. A ausência é segura: séries sem fim são encerradas via scope following/all.

⚡
Badge de recorrência deve mostrar o tipo (mensal, semanal)?
O ícone Repeat é simples e claro. Uma alternativa é mostrar um texto curto como "Mensal" ou "Semanal" ao lado do ícone. Impacto na densidade da linha — considerar o layout atual de TransactionItem.
→ Decidir antes do Slice 3
